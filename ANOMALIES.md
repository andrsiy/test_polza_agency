# ANOMALIES.md — review.csv

`data_pack/review.csv` был описан как «свежая выгрузка для той же базы». На деле это не совсем так.
Всё, что описано ниже, найдено сверкой `review.csv` с 994 компаниями, уже загруженными из
`page_*.json`, а также скриптовой валидацией каждого поля (`scripts/load-reviews.ts`). Для каждой
находки указан способ обнаружения, чтобы её можно было перепроверить.

## 1. Это не «отзывы» — это, скорее, ещё компании

Заголовок — `id,name,category,city,address,rating,reviews_count,site,phone` — побайтово та же схема,
что и в JSON-выгрузке. Нет ни текста отзыва, ни автора, ни даты отзыва — ничего, что реально делало бы
это таблицей «отзывов». Загружать это отдельной таблицей `reviews` было бы неверно; вместо этого
данные были объединены (upsert) с той же таблицей `companies`.

*Как обнаружено:* прочитал заголовок CSV и сравнил со схемой элементов JSON.

## 2. Шесть записей в другом, не связанном с остальными, диапазоне id

6 строк используют id вида `c_900006`–`c_900011`, тогда как все остальные записи в обоих файлах
используют диапазон `c_000001`–`c_001200`. Названия этих компаний также нарушают конвенцию именования,
принятую везде: любое название ООО/АО в остальном корпусе данных в кавычках («ООО «Вектор Плюс»»), а
эти шесть — без кавычек (`АО Флагман Лаб`, `Прайм Плюс`, `АО Сокол`, `АО Сокол Лаб`, `Модуль Строй`,
`АО Орион Групп`). Больше в них ничего не сломано — они нормально парсятся и выглядят как реальные
компании — но сочетание отдельного диапазона id и другого стиля именования — сильный сигнал, что они
попали из другого источника/датасета. Оставлены в загрузке (это не невалидные данные), но помечены в
выводе скрипта для ручной проверки.

*Как обнаружено:* поиском id по маске `^c_9\d{5}$` и сравнением формата названий с остальным файлом.

## 3. Строка с пропущенным значением category сдвигает все последующие колонки

`c_001015` в исходном CSV:

```
c_001015,АО «Платформа»,Пермь,"ул. Советская, д. 89, офис 43",,4.2,77,,+7 (383) 920-78-13
```

Категория пустая, поэтому всё, что после неё, сдвигается на одну колонку влево: реальный город
(«Пермь») попадает в колонку `category`, реальный адрес попадает в колонку `city`, а `address`
оказывается пустым. Настоящее значение category потеряно безвозвратно — восстановить его нельзя —
поэтому эта строка отбрасывается загрузчиком, а не угадывается (зафиксировано в отчёте об аномалиях).

*Как обнаружено:* эвристикой в загрузчике — если колонка `city` содержит что-то похожее на уличный
адрес (`^ул\.|просп\.|...`), строка почти наверняка сдвинута.

## 4. Дублирующиеся id внутри самого review.csv

`c_001075`, `c_001049`, `c_001050` — каждый встречается в файле дважды, оба раза с одинаковыми
значениями. Безобидно — `ON CONFLICT (id) DO UPDATE` в загрузчике означает, что вторая копия просто
перезаписывает те же значения — но стоит отметить, поскольку наивный `INSERT` без обработки конфликта
завершился бы ошибкой.

*Как обнаружено:* подсчётом повторяющихся id в распарсенном CSV.

## 5. Две полностью пустые строки в конце файла

Последние две строки данных — это запятые без содержимого между ними (`,,,,,,,,`) — не повтор
заголовка, не частичные данные, а просто пусто. Пропущены загрузчиком.

*Как обнаружено:* проверкой, что все поля строки после trim становятся пустой строкой.

## 6. rating: пять разных видов некорректных значений

Подсчёт сырых значений колонки `rating`:

| сырое значение | кол-во | проблема |
|---|---|---|
| `N/A` | 1 | нечисловая заглушка вместо пустой ячейки |
| `4,5` | 1 | запятая как десятичный разделитель (RU-локаль) вместо точки |
| `-3` | 1 | отрицательное значение, вне шкалы рейтинга 0–5 |
| `7.2` | 1 | выше шкалы 0–5 |
| *(пусто)* | 20 | обычное отсутствующее значение, аналог `null` в JSON-источнике |

Загрузчик нормализует случай с запятой (`4,5` → `4.5`), а остальное (`N/A`, значения вне диапазона)
трактует как отсутствующее значение, а не вставляет то, чему нельзя доверять. В схеме также есть
constraint `CHECK (rating BETWEEN 0 AND 5)`, так что значения вне диапазона не смогут незаметно
проникнуть обратно.

*Как обнаружено:* подсчётом (`Counter`) по сырой колонке `rating` и попыткой числового парсинга
каждого значения.

## 7. reviews_count: отрицательные, нецелые и нечисловые значения

| сырое значение | проблема |
|---|---|
| `-10` | отрицательное количество |
| `45.5` | не целое число |
| `много` | вообще не число |

Все три случая трактуются как невалидные и по умолчанию заменяются на `0` (с пометкой в отчёте об
аномалиях), а не тихо приводятся к типу как попало (например, `Number("много")` даёт `NaN`, что иначе
превратилось бы в `NULL` и нарушило бы constraint `NOT NULL` на этой колонке).

*Как обнаружено:* парсингом каждого значения `reviews_count` как целого числа и проверкой результата.

## 8. phone: мусорные и обрезанные значения

- `8 (925) abc-12-34` — буквы внутри номера, и `8` вместо `+7`.
- `+7` — обрезан, реальных цифр нет.
- В 22 строках вместо отсутствия `phone` стоит пустая строка — в JSON-выгрузке для отсутствующего
  телефона используется `null`, в CSV — `""`. Оба варианта нормализуются в SQL `NULL`.

Значения, не соответствующие формату `+7 (XXX) XXX-XX-XX`, используемому везде остальными записями,
отбрасываются (устанавливаются в `NULL`), а не сохраняются как непригодный к использованию текст.

*Как обнаружено:* сверкой каждого значения телефона по regex с форматом, который используют ~890
корректно оформленных номеров в JSON-выгрузке.

## 9. site: та же несогласованность null/пустая строка, что и у phone

В 60 строках `site` — пустая строка вместо отсутствующего значения. При загрузке нормализуется в
`NULL`.

## 10. city: шесть разных написаний двух реальных городов

| сырое значение | исправление |
|---|---|
| `Moscow` | → `Москва` (не на том языке) |
| `москва` | → `Москва` (не тот регистр) |
| `Москва ` | → `Москва` (лишний пробел в конце) |
| `Санкат-Петербург` | → `Санкт-Петербург` (опечатка) |
| `РњРѕСЃРєРІР°` | → `Москва` (мойибake) |
| `РЎР°РЅРєС‚-РџРµС‚РµСЂР±СѓСЂРг` | → `Санкт-Петербург` (мойибake) |

Две «кракозябры» — это UTF-8-текст, который где-то выше по цепочке был декодирован как Windows-1251 и
пересохранён обратно в UTF-8 — классический мойибake (подтверждено обратным преобразованием: строка
кодируется как `windows-1251`, а получившиеся байты декодируются как UTF-8, что точно восстанавливает
исходный кириллический текст). Если бы это не исправить, наивный `GROUP BY city` дал бы 6 фантомных
«городов» вместо реальных 2, что напрямую исказило бы запрос «средний рейтинг по городам» из задачи 1.

*Как обнаружено:* подсчётом (`Counter`) по сырой колонке `city` и визуальной проверкой всего, что не
входит в список 20 известных городов из JSON-выгрузки; строки-мойибake подтверждены обратным
преобразованием через кодек cp1251.

## Итоговый эффект на базу данных

- 207 строк данных в файле → 2 пустые строки и 1 строка со сдвинутыми колонками отброшены → 204
  строки прошли валидацию и были загружены (upsert).
- Из этих 204: 6 уже существовали (идентичные значения, обновление без изменений), 3 были дублями друг
  друга внутри файла, в итоге **195 действительно новых компаний** добавлено в `companies`
  (994 → 1189 всего).
- 6 записей сохранены, но помечены как вероятно происходящие из другого источника (см. §2).

Запусти `npm run db:load-reviews`, чтобы воспроизвести — скрипт выводит тот же отчёт (счётчики строк +
строка на каждое исправленное/помеченное поле) в stdout.
